# 按配送档案分箱 + 支付拆合引擎（设计文档）

日期：2026-08-28
范围：nshop checkout 结算模型重构 —— 配送分箱与支付聚合

---

## 1. 背景与问题

### 1.1 现状
- 商品变体 `customFields.shippingProfileId` 绑定「配送档案」（ShippingProfile），档案含允许的配送方式与自提点。
- 现有 checkout **整单选一个配送方式**，多商品约束取「交集」（`getIntersectedShippingMethods` / `getIntersectedPickupLocationsWithConfig`）。

### 1.2 交集模型不可行
当购物车同时含「门店自提 / 职工自提 / 顺丰」等多互斥配送约束时，交集为空 → 整单无解。实际业务希望**每个配送档案各走各的方式**，而非强行交集。

### 1.3 设计目标（用户定稿）
- **不同租户**商品 → 必分箱。
- **同租户、不同配送档案** → 必分箱。
- **同配送档案** → 可合箱一起配送。
- **零交集运算**：配送档案即为唯一分箱划分单元。

## 2. 支付档案与支付约束

### 2.1 支付档案绑定配送档案
- 每个租户有「支付档案」（PaymentProfile），**根据配送档案设置**。
- 配送档案内商品 → 使用同一支付档案。
- 所有支付档案**必含「余额」支付方式**（基础方式）。

### 2.2 绑定规则（支付档案 ↔ 配送档案）
- 支付档案与配送档案**同租户、可互相引用**：一个配送档案对应一组支付方式集合（即其绑定的支付档案）。
- 分箱后，每箱的支付方式 = 该箱配送档案所绑定的**支付档案**提供的支付方式。
- 全局支付档案 / 全局配送档案（`isGlobal=true`）：由超管维护，任意租户可选。
- 租户级档案（`isGlobal=false`）：仅本租户可见，ownerChannelId 限定。
- 允许的支付方式白名单存在 PaymentProfile 内；余额为所有档案的内建基础方式。

### 2.3 默认档案回退规则（未指定档案的特殊情况）
> 某些商品可能**未绑定任何配送/支付档案**，或所绑档案被停用。

- **配送侧**：变体未绑定配送档案 / 档案被停用 → 回退到**该租户的默认配送档案**（`ShippingProfile.isTenantDefault`）。若仍无，则走该租户全局可见的默认配送方式列表。
- **支付侧**：同样对称回退到**该租户默认支付档案**（`PaymentProfile.isTenantDefault`）；若仍无，回落租户默认支付方式集合。
- 停用档案一律**不参与**任何绑定匹配（配送与支付服务均已实现 `resolveEffectiveProfileIds` 排除停用档案）。
- **对合并的影响**：未指定档案的商品会并入"默认档案分组"而非自成一箱——因此它可能与其它同默认档案商品合箱；其支付方式跟随默认支付档案，参与余额合单/非余额判断，规则与普通箱完全一致。
- 已由后端支撑：`ShippingProfileService.getTenantDefault`、`ShippingProfileService.resolveEffectiveProfileIds`、`PaymentProfileService.getTenantDefault`、`PaymentProfileService.resolveEffectiveProfileIds`。

### 2.4 支付聚合规则（三档）
| 所选支付方式 | 可合并性 | 订单形态 |
|---|---|---|
| **余额支付** | 跨租户、跨档案**全部可合并** | 1 个订单：多 fulfillment + 一次余额扣款 |
| **非余额方式 M（同租户）** | 仅当**每个分箱的支付档案都含 M** → 合并；缺 M 的箱拆出 | 尽量合单，缺 M 拆独立单 |
| **非余额方式 M（跨租户 / 方式不同）** | 不合并 | 拆成多个独立订单 |

### 2.5 余额资金模型
- **全局一个共享钱包**：所有租户商品共用，余额总合并清算。
- 跨租户/跨档案合单时，余额一次性从共享钱包扣除。

## 3. 整体架构：一骨架 + 支付决定拆合

底层统一 **Path A 骨架**（单订单多 fulfillment），支付方式决定是否/如何拆成独立订单：

```
                       结账入口
                          │
                1. 按配送档案分箱（唯一划分单元）
                          │
                2. 用户选择支付方式 M
                          │
                3. 聚合引擎判定 M 的合并能力
                ┌─────────┴─────────┐
            M = 余额              M = 非余额
                │                    │
      全部箱 → 1 个总订单      每箱是否都含 M？
      (多 fulfillment) <<<< 同租户全含→合单
                               缺 M / 跨租户→拆独立单
                │                    │
         余额一次扣款          各自独立支付
```

### 3.1 关键原则
- **不维护两套订单系统**；把 Path B 视为「支付不可合并时的降级拆分」，而非平行实现。
- **一条流水线，两种成交外观**：
  - 选余额 → 自动合一单（Path A 体验）
  - 选非余额 + 跨档案/跨租户 → 自动多单（Path B 体验）

## 4. 使用案例推演

> 购物车：某1（档P1·门店自提·a点）、某2（档P2·职工自提·B/C点）、某3（档P3·自提全市/顺丰·租户b）、某4（档P1·门店自提·a点，与某1同档案）

```
购物车
│
├─ 【档 P1】（某1 + 某4）→ 合箱 ✓
│     └─ 配送方式：门店自提 @ a自提点
│
├─ 【档 P2】（某2）→ 独立一箱
│     └─ 配送方式：职工单位自提 @ {B, C}点
│
└─ 【档 P3】（某3）→ 独立一箱（租户b）
      └─ 配送方式：自提点全市 或 顺丰
```

- **选余额** → P1+P2+P3 合并为一个总订单，3 个 fulfillment 分箱，余额一次扣款。
- **选微信（同租户 a、非 P3 不支持或跨租户）** → P1、P2 尽量合单（若都在租户 a 且都支持微信），P3 拉出成独立订单。

## 5. 拆分 / 合并的判定实现

### 5.1 分箱（订单内部）
```
groupKey = shippingProfileId（按档案分组）
Box = { profileId, variants[], shippingMethods[], pickupLocations[] }
```
- 每组箱内独立单选配送方式/自提点。
- 每组生成一个 fulfillment。

### 5.2 合并判定（聚合引擎，纯函数）
```
function decideAggregation(boxes, selectedPaymentMethod):
    if selectedPaymentMethod == BALANCE:
        → 全部 boxes 进 1 个订单
    else:
        for box in boxes:
            if !paymentProfile(box).methods.includes(M):   → 需拆
            if tenant(box) != tenant(prev box):            → 需拆
        → 可合并的进同一订单，需拆的独立订单
```

### 5.3 余额扣款
- 共享钱包账户扣减总订单金额。
- 每个 fulfillment 关联其 box 的配送/费用明细。

## 6. 前端结算体验（余额合单外观）

- **一个订单、按箱展示配送与总额**：
  - 顶部一个总价。
  - 每 box（配送档案）展示配送方式、自提点、配送费小计。
  - 底部余额一次性扣款。
- 非余额拆分时：渲染为多笔待支付订单，各按箱支付。

## 8. 决策记录（已获用户确认）
1. 分箱粒度 = 配送档案；同档案合箱、跨档案/跨租户分箱；零交集。
2. 底层统一 **Path A 骨架**，支付决定拆合。
3. 余额 = **全局共享钱包**，跨租户/跨档案合并成总订单。
4. 余额合单外观 = 一个订单、按箱展示配送与总额。
5. 既支持余额合单，又支持非余额拆单，一条流水线。
6. **默认档案回退**：未绑定/停用档案的商品回退租户默认配送+支付档案，并入默认分组，不因缺失而自扰合单逻辑。
7. 支付档案按配送档案绑定：每箱支付方式 = 其配送档案绑定的支付档案白名单；余额为全档案内建基础方式。
